# CGP Certificate Manager

Автоматическое управление сертификатами Let's Encrypt для многодоменного почтового сервера CommuniGate Pro. Использует Certbot, Cloudflare DNS-01 и локальный HTTP CLI CommuniGate.

[English documentation](README.md)

В этой ветке разрабатывается **2.2.0.dev4**. Стабильный релиз для действующего
сервера — **2.1.0**. План, отметки о выполнении и точка продолжения находятся
в [ROADMAP.md](ROADMAP.md) и [DEVELOPMENT.md](DEVELOPMENT.md). Ветка разработки
ещё не является релизом.

## Возможности

- Обнаружение доменов и псевдонимов, исключение IP-адресов, поддержка IDN, wildcard и SAN.
- Проверка доступности зон Cloudflare и DNS-делегирования; защита от сокращения SAN при потере доступа к зоне.
- Автоматическое продление и установка сертификатов без запроса перезапуска CGServer.
- Полная цепочка CA в формате объединённых DER-сертификатов, активация PKI через CertificateType=YES.
- Проверка соответствия ключа, чтение параметров после записи, проверка TLS, SNI, имени и отпечатков полной цепочки.
- Резервные копии, восстановление при ошибке установки, раздельный backoff, история и SMTP-уведомления.
- Журнал транзакций до изменения CGP, восстановление после прерывания, проверка TLS по сохранённому сертификату и его цепочке независимо от файлов Certbot.
- Проверка владельца, прав, типа и ссылок у конфигурации, токенов, состояния, истории, резервных копий и файла блокировки перед использованием.
- Диагностика явных и эффективных полей сертификата; блокировка неполного, наследуемого, пустого, нечитаемого или меняющегося снимка до обычного выпуска и установки.
- Плановое обслуживание через systemd.

## Установка

Проверенная среда: Ubuntu 24.04 LTS. Необходим локальный HTTP CLI CommuniGate с правами чтения и изменения настроек обслуживаемых доменов. API-токен Cloudflare должен иметь права Zone Read и DNS Edit для соответствующих зон.

    sudo apt update
    sudo apt install certbot python3-certbot-dns-cloudflare python3-dnspython python3 openssl ca-certificates dnsutils iproute2
    git clone https://github.com/alphazulu/cgp-certificate-manager.git
    cd cgp-certificate-manager

Для новой установки создайте конфигурацию:

    sudo install -d -m 700 /etc/cgp-letsencrypt
    sudo install -m 600 examples/config.example.json /etc/cgp-letsencrypt/config.json
    sudo install -m 600 examples/cloudflare.example.ini /etc/cgp-letsencrypt/cloudflare.ini
    sudoedit /etc/cgp-letsencrypt/config.json
    sudoedit /etc/cgp-letsencrypt/cloudflare.ini
    sudo bash install.sh

При обновлении не перезаписывайте действующую конфигурацию примерами. Установщик сохраняет резервную копию прежней версии и оставляет таймер остановленным. Certbot-сертификаты сохраняются.

CLI должен быть доступен через loopback, например http://127.0.0.1:8100/CLI/. По умолчанию проверяется HTTPS на порту 443. При необходимости задайте tls (host, port, sni, starttls). Параметры domains позволяют задать enabled, wildcard, extra_names, exclude_names, cert_name и tls. Для нескольких аккаунтов Cloudflare используйте cloudflare_accounts с путями credentials. Для SMTP-уведомлений настройте notifications.

Версия разработки требует, чтобы все четыре прежних поля сертификата были явно заданы, читаемы, непусты и совпадали с эффективными значениями. Это проверяется до обычного выпуска и установки. Для диагностики используйте `--bootstrap-check`. Автоматическая первоначальная установка остаётся заблокированной: новый домен требует подготовленного администратором рабочего сертификата и проверки перед автоматизацией.

## Проверка и запуск

    sudo cgp-letsencrypt --sync
    sudo cgp-letsencrypt --doctor
    sudo cgp-letsencrypt --plan
    sudo cgp-letsencrypt --domain example.com --dry-run
    sudo cgp-letsencrypt --domain example.com
    sudo cgp-letsencrypt --verify
    sudo systemctl start cgp-letsencrypt.service
    sudo systemctl enable --now cgp-letsencrypt.timer

Замените example.com на свой домен. Отключайте certbot.timer только если все его сертификаты обслуживаются менеджером.

## Готовность к замене сертификата

```sh
cgp-letsencrypt --bootstrap-check --domain example.com --json
```

Команда доступна в ветке разработки. Она читает настройки через локальный CGP
CLI, не создаёт состояние или файл блокировки и показывает только имена полей,
их происхождение и безопасные причины отказа. Значения ключей и сертификатов в
отчёт не попадают. Повреждённый или меняющийся ответ означает неизвестное
состояние, а не отсутствие полей. Без `--domain` проверяются домены из CGP;
код завершения — 1 при блокировке хотя бы одного домена, 0 для пустого списка
или полностью пригодных снимков.

Обычный запуск, установка и `--plan`/`--doctor` проверяют готовность заранее.
Принудительное продление и повтор не обходят защиту. Установка повторяет
проверки после сохранения фаз журнала и при чтении результата. Просроченный
полный снимок не блокируется только из-за срока; готовность снимка не является
проверкой TLS. `--dry-run` сохраняет прежний режим Certbot staging и DNS-запросов.

Bootstrap с отсутствующими полями ещё требует экспериментов на отдельном CGP:
нужно подтвердить удаление конкретных PKI-полей, побочные эффекты и точное
восстановление отсутствия. Контракт и план этих проверок описаны в
[docs/BOOTSTRAP.md](docs/BOOTSTRAP.md).

## Восстановление прерванных операций

Перед новым выпуском, установкой и ручным откатом менеджер разрешает оставшиеся
транзакции под общей блокировкой. Если незавершённый журнал появился во время
текущего запуска, обработка останавливается до изменения следующего домена.
Диагностические команды не запускают восстановление. Для этих двух команд
доступ к Cloudflare не требуется:

```sh
sudo cgp-letsencrypt --transactions --json
sudo cgp-letsencrypt --recover --domain example.com
sudo cgp-letsencrypt --transactions
```

Просмотр показывает только домен, фазу, распознанное состояние CGP и совпадение
идентификатора сервера. Приватные ключи в вывод не попадают. Пустой результат
означает отсутствие незавершённых журналов, но не новую проверку TLS. Успешный
просмотр возвращает код 0 даже для строк `unknown` или `foreign`; ошибка
восстановления возвращает ненулевой код.

Журнал хранит предыдущие и новые параметры вместе с отдельными TLS-адресами
и SNI. Поэтому восстановление старого сертификата работает и после изменения
SAN в новой версии Certbot. Если параметры CGP не совпадают ни с одним
сохранённым снимком, менеджер сохраняет журнал и отказывается от записи.
Если старые параметры восстановлены, но проверка TLS не прошла, журнал также
остаётся незавершённым.

Файлы находятся в `/var/lib/cgp-letsencrypt/transactions/` и содержат приватные
ключи: каталог имеет права 0700, файлы — 0600. Не публикуйте их и не удаляйте
для обхода блокировки. Сначала проверьте журнал службы и фактические параметры
CGP. Изменение CLI URL или перенос журнала на другой сервер требует отдельного
разбора: автоматическое восстановление намеренно блокируется. Подробнее:
[механизм и ограничения транзакций](docs/TRANSACTIONS.md).

### Принятие прежних настроек без подтверждения TLS

Если транзакция находится в фазе `prepared` или `restoring`, а все четыре
параметра сертификата в CGP совпадают с сохранёнными прежними настройками,
администратор может явно принять их непроверенное состояние:

```sh
sudo cgp-letsencrypt --acknowledge-restored --domain example.com --json
sudo cgp-letsencrypt --acknowledge-restored --domain example.com \
  --confirm-transaction TOKEN_FROM_PREVIEW \
  --reason 'Старый сертификат просрочен; принимаю состояние без подтверждения TLS' --json
```

Первая команда только показывает решение и токен. Вторая требует этот токен и
причину, сохраняет полный исходный журнал в частном каталоге `resolutions` и
возвращает `acknowledged_unverified`. Настройки CGP при этом не изменяются,
успешная проверка TLS не заявляется. Неизвестное состояние, другой сервер и
устаревшее подтверждение вызывают отказ.

Прерванное подтверждение продолжает блокировать обычное восстановление и
изменения сертификатов, даже если исходный pending-файл уже удалён. Завершить
его можно только явным повтором с тем же токеном и причиной. Процедура также
доступна из меню домена и F9. Подробности и порядок действий после прерывания:
[docs/RESOLUTION.md](docs/RESOLUTION.md).

## Проверка DNS и адаптивное ожидание TXT

```sh
sudo cgp-letsencrypt --dns-check --json
sudo cgp-letsencrypt --dns-check --domain example.com
sudo cgp-letsencrypt --dns-transactions --json
sudo cgp-letsencrypt --dns-cleanup
```

`--dns-check` читает конфигурацию, список доменов и зон, затем публичный DNS.
Команда не создаёт состояние или блокировку, не изменяет DNS/CGP и не запускает
Certbot. Она проверяет CAA для Let's Encrypt, признаки DNSSEC в ответах
доверенных резолверов Cloudflare и Google через HTTPS, родительское
делегирование, авторитетные NS и зону `_acme-challenge`. Это не локальная
проверка DNSSEC-подписей и не доказательство видимости из любой точки мира.
Неоднозначные ответы, неизвестная привязка CAA к ACME-аккаунту и неподдерживаемая
делегация challenge вызывают отказ с безопасным кодом причины.

Существующие настройки сохраняют фиксированную задержку. Адаптивный режим
включается явно добавлением в JSON:

```json
"dns_propagation": {
  "mode": "adaptive",
  "timeout_seconds": 300,
  "poll_interval_seconds": 5
}
```

Это фрагмент существующей конфигурации; `dns_preflight` должен оставаться
включённым. Новый authenticator ждёт фактические значения текущего набора
challenge на каждом назначенном NS и в обоих рекурсивных представлениях.
Нужны два свежих успешных прохода. Тайм-аут останавливает выпуск до отправки
ответа на ACME challenge. Несколько TXT, в том числе для apex и wildcard,
обрабатываются совместно; посторонние значения не удаляются.

Права на созданные записи фиксируются в частном журнале
`/var/lib/cgp-letsencrypt/dns-challenges/`. Просмотр `--dns-transactions` не
обращается к API; `--dns-cleanup` под общей блокировкой повторяет очистку
подтверждённо собственных записей. Неопределённый POST, изменение записи
администратором или другой сервер сохраняют блокирующее свидетельство.

Для адаптивного режима нужен Certbot в системном Python; snap не поддерживается
этим способом запуска. Для самостоятельного продления такой lineage служит
установленный `cgp-certbot renew`. Обновление не переписывает renewal-файлы,
не форсирует выпуск и не переводит существующие сертификаты на новый плагин
автоматически. Полный контракт, ограничения и порядок восстановления:
[docs/DNS.md](docs/DNS.md). Этот этап ещё не проверялся на действующем сервере.

## Безопасность и ограничения

Конфигурация находится в /etc/cgp-letsencrypt, состояние и резервные копии в /var/lib/cgp-letsencrypt, сертификаты Certbot в /etc/letsencrypt. Не публикуйте пароли, токены и приватные ключи. Резервные копии должны быть доступны только root. Rollback выполняется через API и не является атомарной транзакцией CGP. Проверка CAA консервативна; DNSSEC опирается на выбранные HTTPS-резолверы. Эти проверки не заменяют проверку центра сертификации. Не все TLS-слушатели поддерживают SNI.

В версии разработки частные каталоги состояния должны принадлежать эффективному UID процесса и иметь права `0700` или строже. Частные файлы должны быть обычными файлами того же владельца, с правами `0600` или строже и одной жёсткой ссылкой. При установленном запуске владельцем является root. Символические ссылки и небезопасные родительские каталоги отклоняются. Доверенный каталог конфигурации, принадлежащий root и имеющий права `0755`, допустим, если его частные файлы отвечают указанным требованиям.

CLI и установщик проверяют дерево частного состояния до внешних операций. Установщик передаёт открытый дескриптор проверенной блокировки своему shell-процессу и удерживает её до завершения установки или обрабатываемого отката. Небезопасные объекты не исправляются автоматическим изменением прав или владельца. Обычные ссылки Certbot в `live` остаются поддерживаемыми и не относятся к этому частному хранилищу. Точные правила, границы защиты и диагностика без вывода содержимого приведены в [docs/STORAGE.md](docs/STORAGE.md).

    journalctl -u cgp-letsencrypt.service -n 100 --no-pager
    python3 -m unittest discover -s tests -v

Стабильная версия 2.1.0 проверена после обновления действующего сервера. Версия разработки ещё не проверялась на нём. Модульные тесты, локальный TLS-сервер и проверки аварийного завершения процесса не заменяют проверку конкретной инсталляции. Независимый проект; лицензия пока не выбрана.

## Опциональный TUI

Установите whiptail командой sudo apt install whiptail. Запустите sudo bash install.sh --tui для интерактивной настройки или sudo bash install.sh --non-interactive с готовой конфигурацией. При обновлении по умолчанию сохраняются настройки. Для изменения настроек после установки используйте sudo cgp-letsencrypt --tui. Мастер позволяет настроить CGP, несколько токенов Cloudflare, домены, wildcard и SAN, email ACME, задержку DNS, TLS и SMTP. Новые установки по умолчанию требуют выбора доменов. Сохранение не выпускает сертификаты и не включает таймер. Проверка прав DNS Edit выполняется отдельно через dry-run. Главное меню и основные запросы доступны на русском и английском, часть диагностических сообщений пока на английском. Можно настроить TLS отдельного домена и расписание. После изменения расписания в установленной системе выполните sudo cgp-letsencrypt --apply-schedule. Команда применяет drop-in systemd, но не включает остановленный таймер. Установщик применяет расписание автоматически.

### Выход из мастера настройки

Первые два пункта меню — «Сохранить и выйти» и «Выйти без сохранения». Кнопка «Выход» и Escape в главном меню запрашивают подтверждение при наличии изменений. Во вложенных меню кнопка «Назад». Ctrl+C прерывает работу. Отмена интерактивной установки прекращает её до копирования приложения и systemd units. Самостоятельный настройщик возвращает код 3 при отмене и 0 при сохранении.

## Административная консоль

После установки: `sudo cgp-letsencrypt --console`. Из тестовой копии: `sudo python3 -m cgp_cert_manager.console`. Консоль curses показывает снимок статуса доменов, SAN, сроки, сведения о таймере и журналы. Enter — операции выбранного домена, F2 — настройщик whiptail, F5 — обновить, F6 — журнал, F7 — таймер, F8 — проверить все домены, F9 — просмотр и восстановление транзакций, Q/Escape/F10 — выход. Операции изменения сертификатов, восстановления и управления таймером требуют подтверждения. Команды выполняются синхронно с обычным выводом терминала. Основная навигация доступна на русском и английском. Статус ready не означает проверенный TLS: для этого выполните Verify.

### Статусы и резервные копии консоли

F1 — справка, S — сортировка, F — фильтр. Цвета различают готовность, результат TLS, истечение срока и ошибки. F8 или проверка выбранного домена фиксирует результат TLS в текущей сессии; обновление статуса сбрасывает отметку. Доступен журнал отдельного домена. При rollback можно выбрать конкретную резервную копию; CLI: `--rollback DOMAIN --backup-file FILENAME`. Теперь откат сам проверяет реальный TLS по выбранной резервной копии. В меню домена доступны его транзакции. F9 работает и при пустом списке доменов: просмотр и восстановление всех журналов доступны независимо от обнаружения доменов.

### Проверка установки и обновления

Оба интерфейса используют сохранённый язык для основных элементов навигации и запросов. Технические статусы и часть диагностических сообщений остаются английскими. Перед включением таймера выполните тесты и проверку TLS. Установщик проверяет синтаксис Python до изменения приложения. Установщик использует общую блокировку и пытается восстановить предыдущую версию, конфигурацию и systemd units при обрабатываемых ошибках. После успешного обновления таймер остаётся остановленным. Сам установщик приложения не защищён транзакционным восстановлением от SIGKILL или отключения питания: новый журнал относится к операциям сертификатов.

## Тестирование

Стабильная 2.1.0 прошла 188 модульных тестов. В ветке разработки новый код сопровождается юнит-тестами; добавлены аварийное завершение и восстановление в новом процессе, настоящий OpenSSL и локальный TLS-сервер. CI требует 100% покрытия строк и ветвей и проверяет чистую установку, обновление с 2.0.1 и 2.1.0, откат, блокировки и сохранение незавершённых журналов в одноразовых контейнерах Ubuntu с имитацией systemd. Актуальные результаты зафиксированы в DEVELOPMENT.md. Покрытие не заменяет тестирование реального CGP и ACME.

Для текущего этапа явного разрешения транзакций локально прошли **455 тестов**: **2073 оператора / 844 ветви / 100% покрытия**. В набор входят 22 проверки аварийного завершения и повторного запуска и 9 проверок настоящего OpenSSL и локального TLS. Сценарии установщика также проверяют сохранность аудита и 24 отказа при небезопасных путях для каждой исходной версии. Точные подтверждённые результаты CI приведены в [DEVELOPMENT.md](DEVELOPMENT.md). Проверка на действующем сервере остаётся отдельным этапом.

    python3 -m coverage run --branch --source=cgp_cert_manager -m unittest discover -s tests -v
    python3 -m coverage report -m --fail-under=100

## Обновление с 2.0.1

Из отдельной копии доверенного релиза выполните `sudo bash install.sh --upgrade`, затем `sudo cgp-letsencrypt --version`, `--doctor`, `--plan`, `--verify`. Проверьте указанный установщиком путь резервной копии. Только после успешной проверки включите таймер командой `sudo systemctl enable --now cgp-letsencrypt.timer`. Установщик не выпускает сертификаты.
