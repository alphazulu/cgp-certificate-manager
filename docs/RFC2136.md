# RFC2136 adaptive DNS provider

Checkpoint 17 (`2.2.0.dev14`, unreleased) adds an explicitly selected RFC2136
provider to the existing supervised `cgp-dns` authenticator. Cloudflare remains
the default when `dns_provider` is omitted. Stable production is still `2.1.0`.
Real DNS-provider, ACME and VM/server acceptance remains deferred; isolated
protocol tests do not establish compatibility with a particular DNS deployment.

## Supported boundary

This provider supports **adaptive mode only**. It uses configured zones and
primary IP addresses, authenticated DNS over TCP, HMAC-SHA256 TSIG, complete
TXT RRset prerequisites and the existing durable challenge receipts. It does
not require the separate Certbot RFC2136 plugin or another Python dependency.

The operator must configure an authoritative primary which answers signed
queries and accepts signed updates for the same zone and view. The address may
be a hidden primary; public nameservers are supplied separately for delegation
and propagation checks. An authoritative flag alone does not establish that an
endpoint is the primary. Forwarding secondaries, endpoints with inconsistent
views and automatic primary selection are outside this contract.

The provider uses no AXFR, zone enumeration, server-hostname lookup, UDP
fallback or automatic key/algorithm fallback. Every protocol exchange has a
10-second timeout. Replies must authenticate with the expected key and
algorithm, correspond to the request and be untruncated. TXT reads require
authoritative, exact-owner answers; negative reads require the exact zone SOA.
Successful UPDATE replies may omit the original sections, retain only the
matching zone, or echo the complete request sections. Unrelated zones, partial
echoes, changed TTL/metavalues, extra records and unexpected OPT data refuse.
Aliases, referrals, contradictory data and unsupported record shapes refuse.
The compatibility dependency profile explicitly checks for a TSIG on replies,
because relying on that library version's parser alone would accept unsigned
answers to signed requests.

TSIG authenticates messages; this TCP transport does not encrypt DNS names,
challenge values or ownership metadata. Secret bytes remain in the protected
local credential file and are not placed in command arguments or public status.
Key provisioning and DNS-server policy remain explicit administrator work.

## Explicit configuration

Use the existing protected schema-2 manager configuration. The relevant fragment
is:

```json
{
  "dns_provider": "rfc2136",
  "dns_preflight": true,
  "dns_propagation": {
    "mode": "adaptive",
    "timeout_seconds": 300,
    "poll_interval_seconds": 5
  },
  "rfc2136": {
    "zones": [
      {
        "zone": "example.com",
        "server": "192.0.2.53",
        "port": 53,
        "credentials": "/etc/cgp-letsencrypt/rfc2136.json",
        "key_name": "cgp-acme.example.com",
        "algorithm": "hmac-sha256",
        "nameservers": ["ns1.example.com", "ns2.example.com"]
      }
    ]
  }
}
```

The addresses and domains are synthetic placeholders. A complete manager
example is in [rfc2136.example.json](../examples/rfc2136.example.json). Existing
CGP, domain-selection, schedule and notification settings remain necessary.
Changing the JSON file alone does not reconfigure an existing Certbot renewal
lineage or enable a timer. Follow the separate staging/renewal migration plan
before any production switch.

Configuration is strict:

- Supply 1–128 unique zones. Each zone has an explicit primary IPv4/IPv6
  literal, port 1–65535, absolute credential path, key name and 1–16 unique
  public nameserver names. Port defaults to 53; scoped IPv6 and hostnames are
  refused as primary addresses.
- Zone, key and nameserver names are normalized to lowercase ASCII without a
  final root dot. IDNA input is accepted; TSIG key names may also be a single
  LDH label. Unknown zone-entry keys and duplicate normalized names refuse.
- `hmac-sha256` is the only accepted algorithm and the default. Fixed
  propagation, native Cloudflare/manual hooks and disabled preflight refuse
  before a provider write or Certbot launch.
- The current interactive configuration editor remains Cloudflare-specific.
  With RFC2136 selected it refuses before opening the menu or staging token
  files. Edit the protected JSON configuration explicitly for this backend.

Each credential file must be private under the existing [storage
rules](STORAGE.md), contain only `{"secret":"BASE64"}`, and decode to 32–128
secret bytes. The parser accepts canonical base64 only, rejects duplicate or
extra JSON fields and reads at most 4097 characters to enforce a 4096-character
limit. [rfc2136-secret.example.json](../examples/rfc2136-secret.example.json)
contains an intentionally invalid placeholder, not a usable key. Installer
preflight validates the configured private files without contacting DNS.

## Binding receipts to their original target

New RFC receipts reuse schema 2 with `"provider": "rfc2136"`. Their opaque
`zone` ID is a domain-separated SHA-256 of normalized zone name, primary IP,
port, key name, algorithm and absolute credential path. It is a configuration
binding, not a remote server-generated record ID. The synthetic `record` ID is
the receipt's random ownership nonce.

Both source creation and saved-ledger validation check the exact zone/path
pair, challenge namespace and nonce. Changing a primary, port, key name, zone
or path cannot redirect cleanup: the old receipt refuses until its original
target configuration is restored. Removing a configured zone likewise keeps
its receipt pending. Configuration and receipt files remain trusted private
state; this is not a defense against arbitrary same-UID/root modification.

Secret bytes and the public nameserver list are outside the binding. Rotation
at the same configured key name/path and a normal public-NS adjustment remain
possible, provided the current key still authenticates the required operations.
There is no frozen secret-content snapshot. Status validates bindings without
reading secret contents and preserves the existing public fields `id`, `name`,
`phase`, `owned` and `zone`.

Legacy schema 1 always means Cloudflare. Cloudflare schema 2 retains its
existing meaning. Finish pending receipts with their original provider before
switching the global selection; mixed-provider issuance is not enabled.

## Ownership and persistent generation

For each `_acme-challenge` owner, the provider shares the TXT RRset with foreign
records. Its reserved metadata is:

| TXT value | Lifetime and role |
| --- | --- |
| The actual 43-character DNS-01 value | Present while this owned challenge is active. |
| `cgp-certificate-manager:owner:` followed by a 32-character nonce | One marker for each owned active challenge; removed with that challenge value. |
| `cgp-certificate-manager:generation:` followed by a fresh 32-character nonce | Exactly one persistent generation marker after the first managed mutation. Replaced on each create/delete and retained after cleanup. |

These prefixes are reserved for this provider. Do not remove, roll back, reuse
or manufacture its generation and owner metadata. Multiple or malformed
generation records, malformed owner markers, and owner markers without a
generation refuse automatic work. Ordinary unrelated TXT values remain intact.

Before creation, the session saves intent privately. An already matching TXT
is borrowed and never deleted. Otherwise the provider queries the complete
raw TXT RRset and sends one update conditioned on that exact set, or on its
absence when empty. It removes only the previous generation value, adds a fresh
generation and adds this challenge/owner pair. A readback must observe the pair
and generation before the receipt is marked created.

Cleanup reads the current complete set, verifies the exact owned pair, then
uses another full-set prerequisite to delete only that pair and advance the
generation. Other challenge values, other active ownership markers and foreign
TXT chunks are preserved. Conditional mutations also require no CNAME at the
owner, no DNAME from owner through zone apex, and no more-specific NS cut.
Concurrent changes therefore refuse the update instead of being overwritten.

The persistent generation is necessary even after the ACME value is removed:
cleanup must not recreate an old signed create request's prerequisite state.
A fresh generation changes that state on every mutation, preventing a captured
older update from being applied again while it is still time-valid. This relies
on the server honoring the prerequisites and on reserved metadata not being
restored or deleted outside the protocol.

The snapshot is bounded to 128 TXT records and 32768 bytes of TXT character
data. Creation checks space for its added metadata before sending an update.
Existing TTL is reused, or 120 seconds for an empty set. Prerequisites compare
RDATA, not TTL; concurrent TTL-only changes are outside this protection. The
provider does not replace an entire foreign RRset to normalize its contents.

## Interrupted and uncertain operations

All remote update errors, timeouts, missing acknowledgements and authentication
failures retain intent or the created receipt. Even a signed prerequisite
failure is not enough to discard a create intent: a duplicate signed request
could have applied before the copy which received that failure. Only local
pre-send refusals which have sent no update can retire an unused intent.

Recovery of intent requires the exact canonical challenge value and its nonce
owner marker. It never resends creation blindly. A missing pair after an
uncertain create remains unresolved. One missing member, changed metadata or
lost generation likewise keeps evidence pending.

For a previously created receipt whose pair has disappeared, a signed query
alone is insufficient to retire it. The provider additionally sends an update
with **prerequisites only**, checking the complete observed RRset and alias/cut
guards in the original configured zone. An authenticated successful response
proves that condition without requesting changes to TXT data or its generation. A positive
answer from a newly delegated child cannot substitute for that zone proof.

Use the existing `--dns-transactions` and `--dns-cleanup` commands for explicit
inspection and retry. Completion is durable before receipt removal. The manager
lock and supervised Certbot process lifetime remain unchanged; a pending
receipt blocks new issuance. The persistent generation TXT remains after a
successful cleanup by design.

## Validation and remaining acceptance

Unit, signed-wire, loopback TCP and fresh-process tests accompany this code.
They exercise both dependency profiles, replay and conditional-update races,
ownership preservation, malformed/unsigned/bad-MAC replies, private credential
validation and restart recovery. Exact observed gates and commit/run identities
are recorded in [DEVELOPMENT.md](../DEVELOPMENT.md).

The deferred real-provider acceptance must separately verify the selected DNS
server's signed-query/update policy, exact-set prerequisites and no-op updates,
hidden-primary/public-NS behavior, persistent metadata, multi-value challenges,
interrupted updates and Certbot renewal migration. It is not part of this
checkpoint's isolated tests. See [STAGING.md](STAGING.md).

Protocol references: [RFC2136](https://www.rfc-editor.org/rfc/rfc2136.html),
especially exact RRset prerequisites and section 5's changing marker;
[RFC8945](https://www.rfc-editor.org/rfc/rfc8945.html) for TSIG;
[dnspython updates](https://dnspython.readthedocs.io/en/stable/message-update.html)
and [TCP query support](https://dnspython.readthedocs.io/en/stable/query.html).
